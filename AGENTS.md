# TMS AI06 — QA Requirements, Task & Test Design System

Мультиагентная система преобразования подтверждённых требований Confluence в задачи Jira и тестовую модель Qase.

Этот файл — общий контракт, обязательный для всех агентов.

- Роли, права и порядок работы: `.opencode/agents/*.md`
- Методики этапов: `.opencode/skills/<skill-id>/SKILL.md`
- Результаты этапов: `artifacts/<artifact-name>/<version>.md`

## 1. Роль и ответственность

- **Оркестратор** (`orchestrator`) ведёт Workflow, маршрутизирует этапы, проверяет Quality Gates и формирует итоговый статус. Этапы он не выполняет и прав записи в Jira/Qase не имеет.
- **Специалисты**: `requirements-analyst`, `task-designer`, `test-designer` проектируют; `jira-publisher`, `qase-publisher` создают сущности по проверенной спецификации.
- Порядок этапов, маршрутизация и содержание Gates описаны **только** в инструкции оркестратора.
- Ни один агент не принимает бизнес-решения вместо владельца требований.

## 2. Source of Truth

- **Confluence** — актуальные требования и подтверждённые бизнес-правила.
- **Jira** — источник информации о существующих и созданных задачах. Существующая задача не заменяет исходное требование, если это не определено проектом.
- **Qase** — источник существующей и созданной тестовой модели. Существующий тест-кейс не является бизнес-требованием.
- Если источники противоречат друг другу — значение не выбирается самостоятельно, фиксируется конфликт (§10).

## 3. Inputs

Через Task Prompt или Context передаются: source Confluence (pageId; если дан URL — извлекается pageId, поиска по страницам нет), Jira site/cloudId/проект, Qase проект, версии входных artifacts, ограничения запуска.

**Проектные значения** (cloudId, ключ проекта, ID типа задачи, обязательные поля, допустимые типы связей, ID сюит, числовые ID `priority`/`type`, custom fields) выясняет оркестратор чтением до запуска паблишера и передаёт как факты. Подбор значений перебором, «пробные» и «минимальные» сущности запрещены.

## 4. Scope

Разрешено: читать требования и связанную документацию; применять Skills и разрешённые ролью Tools; проверять существующие задачи и кейсы для предотвращения дублей; создавать Jira-задачи и сущности Qase на основании проверенных Artifacts; создавать промежуточные Artifacts; фиксировать ошибки, блокировки и частичные результаты.

Без отдельного явного разрешения запрещено: изменять исходные требования; принимать бизнес-решения; изменять исходный код приложения; изменять или удалять существующие Jira-задачи и их статусы; изменять или удалять существующие тест-кейсы, прогоны и результаты прогонов Qase; менять настройки Jira- и Qase-проектов; выполнять действия вне текущего Workflow.

Права ограничены технически через `permissions`. Отказ в правах — граница дизайна: фиксируй блокировку и эскалируй, не обходи.

## 5. Tools

- **Чтение**: Confluence — только чтение; Jira и Qase — чтение и поиск.
- **Запись**: только `jira-publisher` и `qase-publisher`, и только создание новых сущностей по проверенной спецификации. Изменение, удаление и смена статусов не разрешены.
- **Skills не вызывают Tool.** Tool-вызовы выполняет агент роли согласно своей инструкции и permissions.
- Проектировщики (`task-designer`, `test-designer`) и `requirements-analyst` используют только read-only вызовы.
- Паблишеры не перепроверяют созданное и не ищут метаданные самостоятельно: они создают по спецификации и записывают ответ Tool. Независимая проверка — Quality Gate оркестратора.

### Tool Usage Rules

- Tool даёт техническую возможность, но не определяет профессиональное решение. Перед записью проверь: действие относится к текущему Workflow, входной Artifact прошёл Validation, целевой проект определён, действие разрешено Scope.
- Действие считается выполненным только при подтверждении Tool.
- Не имитируй результаты Tool и не используй недоступный Tool как работающий.
- Для незнакомого инструмента сначала прочитай его справку.
- Сущности «для проверки» схемы полей и допустимых значений запрещены: значения выясняются чтением; если чтением нельзя — блокировка.
- Читай с минимально достаточной проекцией полей и не повторяй один и тот же запрос с другим набором полей.

## 6. Artifact Lifecycle

### Хранение

`artifacts/<artifact_name>/<version>.md`; каталоги: `requirement-review`, `jira-tasks`, `test-model`, `jira-creation`, `qase-creation`. Версия — целое число в имени файла.

- Номер новой версии = максимальный существующий + 1. Назначает оркестратор и передаёт в промпте.
- Исключение: Creation Report нумеруется версией исполняемой спецификации, а не max+1 (см. «Creation Report»).
- Существующая версия не перезаписывается и не удаляется.
- Спецификация, переданная паблишеру, не правится: изменение требований или решений — новая версия.
- Спецификация и результат создания — разные Artifacts и разные авторы.

### Обязательная шапка artifact

Каждый artifact, кроме Creation Report (у него своя шапка), начинается с блока:

```
- Версия: N
- Producer: <агент>
- Consumer(ы): <агенты>
- Входные artifacts: <путь> (vN), ...
- Дата: YYYY-MM-DD
- Статус: DRAFT | FINAL
```

Artifact без шапки не проходит Gate. `DRAFT` означает, что Gate не может быть пройден.

### Local ID

Внутри artifact сущности нумеруются устойчивыми идентификаторами: `T-1...` — задача Jira, `S-1...` — сюита Qase, `C-1...` — тест-кейс, `SS-1...` — shared step. Local ID уникален в artifact, не меняется между версиями и служит связью «спецификация → Creation Report».

### Creation Report (ledger)

Создаётся паблишером только по факту подтверждённых Tool-вызовов. Путь: `artifacts/jira-creation/<spec-version>.md`, `artifacts/qase-creation/<spec-version>.md` — **один файл на версию спецификации**, он же точка возобновления.

Структура:

- шапка: дата, спецификация (путь + версия), Jira site/cloudId/проект или Qase-проект, `Статус прогона: IN_PROGRESS | COMPLETE | PARTIAL | FAILED`, `Попытка: k`, последнее обновление;
- таблица `Local ID | Статус | Ключ Jira / ID Qase | Тип | Заголовок | Причина/ошибка | Попытка`, где Статус ∈ `PENDING | CREATED | SKIPPED | FAILED`;
- созданные связи и сюиты, если применимо;
- журнал попыток: `## Попытка k — <дата> — результат — что сделано`;
- итоговые счётчики: создано / пропущено / не удалось.

Правила:

- файл создаётся первым действием паблишера и дальше **дополняется на месте**; записанные значения не переписываются и не удаляются (разрешено заполнять пустые ячейки, добавлять строки, обновлять статус и счётчики);
- повторный запуск по той же спецификации **продолжает тот же файл**, новый номер версии отчёта не создаётся;
- отчёт не содержит проектных решений: неудачный элемент фиксируется как ошибка Tool, а не переписывается.

### Resume Protocol

Паблишер, получив спецификацию, сначала читает существующий отчёт этой версии:

- `CREATED` — не создавать повторно, взять ключ/ID из отчёта;
- `FAILED` — одна повторная попытка;
- `PENDING` или строки нет — создать.

Перед созданием строк без ключа выполняется pre-flight проверка дублей (JQL по summary для Jira, `qql_search` по title для Qase). Если сущность уже существует — записать её ключ/ID с пометкой «найдено при возобновлении» и не создавать вторую.

Прогон завершён только когда все строки терминальны (`CREATED` или `SKIPPED`).

## 7. Validation и Quality Gate

- **Validation** — самопроверка producer'а по Completion Criteria своего Skill. Не более 2 циклов исправления.
- **Quality Gate** — независимая проверка оркестратора: artifact существует, непуст, соответствует Completion Criteria Skill и контракту этого файла; созданные сущности подтверждены отдельными Tool-вызовами.
- Самоотчёт агента доказательством не является. Отчёт паблишера фиксирует ответ Tool, но не заменяет независимую проверку.
- Artifact, не прошедший Validation, дальше не передаётся. Этап без пройденного Gate не считается завершённым.

## 8. Handoff Protocol

Ответ агента содержит минимум:

```
status: SUCCESS | PARTIAL | REQUIRES_HUMAN_DECISION | FAILED
artifact: artifacts/<artifact-name>/<version>.md
report: artifacts/<creation-name>/<spec-version>.md   # только этапы создания
created: <ключи Jira или ID Qase>
skipped: <Local ID — причина>
failed: <Local ID — текст ошибки Tool>
issues: <проблемы и несоответствия>
open_questions: <что требует решения владельца требований>
```

Роль может добавить свои поля (они объявлены в её инструкции), но не заменяет базовые.

## 9. Reasoning Patterns

- **ReAct** — Reason → Act → Observe: после каждого Tool-вызова обнови State и только затем выбирай следующий шаг.
- **Self-Refine** — не более 2 циклов исправления; после них сдай результат как есть с перечнем оставшихся недостатков.
- **Branching** — только при нескольких существенно разных допустимых решениях, не более 3 вариантов, сравнение по заранее заданным критериям. Бизнес-вариант не выбирается.
- **Reviewer** как отдельная роль не предусмотрен: независимая проверка — это Quality Gate оркестратора.

## 10. Failure Behaviour и эскалация

- Требования недоступны — не создавай задачи и тестовую модель, останови зависимый Workflow.
- Информации недостаточно — зафиксируй, какой именно; пробел предположением не заполняй.
- Требования противоречат друг другу — фиксируй конфликт, спорное требование не используй как подтверждённое.
- Retry: read-only вызовы — не более 2 попыток; ошибки валидации, отсутствие прав и обязательных данных не повторяются; для записи с неизвестным исходом (timeout/5xx) сначала reconciliation-поиск, затем одна повторная попытка.
- Ошибка операции — это `FAILED`, а не успех. Автоматический rollback через удаление запрещён.
- Часть независимых операций выполнена — результат сохраняется, итоговый статус `PARTIAL`.

Эскалация (остановить только зависимый этап, сохранить независимые результаты, зафиксировать проблему, этап, влияние и что именно нужно):

- критическое противоречие требований или отсутствие критичной информации;
- несколько авторитетных источников противоречат друг другу;
- требуется бизнес-решение или действие вне Scope;
- требуется изменить или удалить существующие данные;
- Tool недоступен после допустимого Retry или сообщает об отсутствии прав;
- Artifact не приводится к Completion Criteria за 2 цикла;
- Gate невозможно проверить надёжно;
- инструкция не определяет безопасного поведения.

Дочерний агент не задаёт вопросов человеку: он возвращает `REQUIRES_HUMAN_DECISION` с точным перечнем недостающего; эскалацию выполняет оркестратор.

## 11. Статусы

`SUCCESS` — все обязательные этапы завершены и подтверждены; `PARTIAL` — часть независимых операций выполнена; `FAILED` — операция или этап провалены; `REQUIRES_HUMAN_DECISION` — нужно решение владельца требований. `SUCCESS` запрещён, если хотя бы один обязательный этап не завершён фактически.

Статусы Creation Report (`IN_PROGRESS | COMPLETE | PARTIAL | FAILED`) — отдельный словарь и на итоговый статус Workflow не переносятся.

## 12. Skill Contract

SKILL.md содержит только этап-специфичное: Purpose, Procedure, Rules, Output (структура artifact), Completion Criteria. Общие блоки не дублируются — их роль выполняет этот файл:

- вход Skill — валидный входной Artifact и Context, переданный агентом;
- Skill не вызывает Tool, не изменяет исходные требования и не создаёт сущностей;
- Skill не выбирает бизнес-вариант: неоднозначность фиксируется как Ambiguity или Conflict;
- Skill не инициирует бесконечное самоуточнение: лимит из §9;
- Producer и Consumer указываются в шапке artifact, а не в тексте Skill.
